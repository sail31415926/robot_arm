# 示教轨迹格式说明

一条示教轨迹 = 存储目录下的一个 YAML 文件 `<name>.yaml`。
存储目录由参数 `teach.storage_directory` 决定，默认 `$HOME/.ros/robot_arm_teach`。

内存表示（`robot_arm_teach/msg/TeachTrajectory`）与文件表示是**同一套字段**，
读写代码在 `src/trajectory_store.cpp`，字段语义的权威定义在 `msg/*.msg` 的注释里。

---

## 0. 三条设计约定（改格式前先读）

**① 记的是完整 6 轴关节轨迹，不是末端位姿序列。**
末端 `gimbal_tool0` 在云台 J4-6 之后，位姿 = f(J1..J6)。存位姿的话回放要重新 IK，
云台回读一有静差就复现不出原轨迹；关节轨迹可以原样喂给 `arm_controller`，是无损的。
要末端位姿就用 FK 现算，文件里不冗余存。

**② 枚举存名字，不存数字。**
`motion_type: DOLLY` 而不是 `motion_type: 1`。存数字的话哪天枚举值变了，
老文件会被**静默**按新语义读出来——一条 DOLLY 变成 TRUCK 不报任何错，只是元数据全错。
存名字读不出来会明确失败。同样规则适用于 `teach_mode`、`arc.rotation`、
`truck.follow_policy`、`crane.direction`。

**③ 运镜参数（`motion_meta`）只是标签，不参与回放。**
回放执行的永远是 `points` 里录下来的关节轨迹。`motion_meta` 全空也能正常回放；
与 `motion_type` 不匹配同样只是元数据不准，不会让机械臂走错。
存它是为了：上层按运镜类型检索、人能看懂这条轨迹当初是怎么示教的、
将来若要做参数化重生成有原始意图可查。

## 1. 完整示例

```yaml
# robot_arm_teach 示教轨迹  格式说明见 robot_arm_teach/doc/轨迹格式说明.md
format_version: 1
name: shot_arc_left_01
created_at: "2026-08-24T15:04:05"
description: 绕主体从 -30 度扫到 +30 度
joint_names: [Joint1, Joint2, Joint3, Joint4, Joint5, Joint6]
motion_type: ARC
teach_mode: JOG
teach_control_mode: 1
sample_rate_hz: 50
raw_point_count: 912
compress_position_eps: 0.002
duration_sec: 18.24
start_positions: [0.0123, -0.4501, 0.9902, 0, 0, 0]
end_positions: [0.6210, -0.4488, 0.9915, 0, 0, 0]
max_velocity: [0.3812, 0.0455, 0.0501, 0, 0, 0]
max_acceleration: [1.2033, 0.3011, 0.2874, 0, 0, 0]
motion_meta:
  subject_label: person_0
  dolly:
    direction: [1, 0, 0]
    distance_m: 0
    keep_camera_facing: false
  truck:
    direction: [0, 1, 0]
    distance_m: 0
    follow_policy: NONE
  arc:
    target_point: [0.4, 0, 0.6]
    radius_m: 0.55
    start_angle_deg: -30
    end_angle_deg: 30
    rotation: CCW
  crane:
    height_delta_m: 0
    direction: UP
points:
  - {t: 0, p: [0.0123, -0.4501, 0.9902, 0, 0, 0], v: [0, 0, 0, 0, 0, 0]}
  - {t: 0.02, p: [0.0143, -0.4501, 0.9902, 0, 0, 0], v: [0.1, 0, 0, 0, 0, 0]}
  # ... 每行一个采样点
  - {t: 18.24, p: [0.621, -0.4488, 0.9915, 0, 0, 0], v: [0, 0, 0, 0, 0, 0]}
```

## 2. 字段表

### 顶层

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `format_version` | uint16 | 当前 **1**。加载时大于本节点支持的版本**直接拒绝**（宁可报错也不要按旧语义误读新文件——这是要驱动实物机械臂的） |
| `name` | string | 轨迹名，同时是文件名。白名单 `[A-Za-z0-9_-]{1,64}`，其余字符一律拒绝（名字来自服务请求，不挡 `/` 和 `..` 就能操作到目录外的文件） |
| `created_at` | string | ISO-8601 本地时间。给人看的，不参与任何间隔计算（间隔一律 steady_clock） |
| `description` | string | 自由备注，可空 |
| `joint_names` | string[6] | 必须恰好是 `Joint1..Joint6`、**逐字同序**。回放前比对，不一致直接拒绝，**不做按名重排**（能重排就意味着能猜，猜错就是走错轴） |
| `duration_sec` | float64 | 总时长 = 末点 `t` |
| `sample_rate_hz` | float64 | 录制时的名义采样频率（50 / 100） |
| `raw_point_count` | uint32 | **压缩前**的原始采样点数。`points` 的长度是压缩后的 |
| `compress_position_eps` | float64 | 当时用的位置阈值（rad），0 = 未压缩 |

### 运镜与示教方式

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `motion_type` | `FREEFORM` / `DOLLY` / `TRUCK` / `ARC` / `CRANE` | 上层应用语义，与底层 ControlMode 完全正交 |
| `teach_mode` | `JOG` / `DRAG` | 示教方式。实机目前只有 `JOG` |
| `teach_control_mode` | 0/1/2/3 | 示教时的**底层** ControlMode 数值（0=TRAJECTORY 1=JOINT_VELOCITY 2=JOINT_EFFORT 3=ADMITTANCE）。点动示教 = 1 |

> `teach_control_mode` 存的是数字而不是名字，是因为它是 `robot_arm_interfaces/ControlMode`
> 的字段（跨仓库的既有定义，不由本包决定），保持与那边的数值一致比自己造一套名字更不容易错。
> 记录它是为了回放/排查时知道这条轨迹是在什么控制通路下采到的——速度模式录的轨迹带位置环
> 滞后，与力矩/导纳拖动录的手感不同，混用时先看这个字段。

### 起终点与包络

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `start_positions` | float64[6] | = `points` 首点位置。冗余存储，让检索和前置校验不必遍历全部点 |
| `end_positions` | float64[6] | = `points` 末点位置 |
| `max_velocity` | float64[6] | 逐轴 \|q̇\| 峰值（rad/s） |
| `max_acceleration` | float64[6] | 逐轴 \|q̈\| 峰值（rad/s²） |

包络的算法（`compute_envelope`）有一个要点：**速度取「录下来的 velocities」与「相邻点位置差分」
两者的较大值**。只信 `velocities` 的话，`/joint_states` 不带 velocity 字段的后端（或云台的开环回显）
会统计出全 0 包络，回放的速度闸就形同虚设——而那恰恰是最需要它拦住的情况。

### `motion_meta`（元数据，不参与回放）

| 段 | 字段 | 说明 |
| --- | --- | --- |
| 通用 | `subject_label` | 被摄主体标签，可空 |
| `dolly` | `direction[3]` / `distance_m` / `keep_camera_facing` | 推进方向（base_link 单位向量）、总距离（拉远为负）、是否全程保持相机朝向主体 |
| `truck` | `direction[3]` / `distance_m` / `follow_policy` | 横移方向、总距离、目标跟随策略（`NONE` / `LOCK_SUBJECT` / `PARALLEL`） |
| `arc` | `target_point[3]` / `radius_m` / `start_angle_deg` / `end_angle_deg` / `rotation` | 环绕目标点（球心）、半径、起止方位角、旋转方向（`CW` / `CCW`）。角度定义与 `ArmTrajectoryShot` 的 azimuth 一致 |
| `crane` | `height_delta_m` / `direction` | 末端高度变化量（带符号）、升降方向（`UP` / `DOWN`，与符号冗余，便于检索） |

无关段留默认值即可。

### `points`

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `t` | float64 | `time_from_start`（s），相对轨迹起点，**严格单调递增**且首点 ≥ 0 |
| `p` | float64[6] | 关节位置（rad），顺序同 `joint_names` |
| `v` | float64[6] | 关节速度（rad/s），同序 |

键名用单字符是为了控制文件体积：50Hz 录 3 分钟 ≈ 9000 点，写全名会让文件大一半。
每个点用 flow style 写成一行，几千点的文件仍然能用眼睛扫。

**严格单调**是硬要求：相邻点时间相等会让 JTC 遇到零时长段（除零 / 无限加速度）。
校验器要求相邻间隔 > 1 µs。

## 3. 压缩语义（`compress_position_eps`）

压缩发生在**录制时**（在线决定保留/丢弃），不是事后处理。保留规则见
`include/robot_arm_teach/teach_recorder.hpp`，摘要：

- 与上一个保留点的逐轴位移都 < `compress_position_eps` → 丢弃
- 三条例外**必须保留**：
  1. 任一轴速度**变号**（运动方向反转 = 轨迹拐点，压掉就削角）
  2. 距上一个保留点超过 `teach.compress_max_gap_sec`（长时间静止也要留锚点，
     否则会出现跨十几秒的长弦，JTC 插值时把「静止」变成「缓慢漂移」）
  3. 首点与末点恒保留

因此压缩**不会**破坏两件事：

- **时间顺序**：只做子集选取，从不重排、不改 `t`
- **速度限制**：两个保留点之间的平均速度 = 被丢掉那段的速度平均值，
  必然不超过该段峰值 → 包络只会变小

`test/test_teach_recorder.cpp` 的 `CompressionNeverIncreasesVelocityEnvelope`
就是在断言后一条。

## 4. 手工编辑与外部生成

允许手写或用脚本生成轨迹文件，但**必须**满足上面所有约束——
加载和回放前都会跑完整静态校验（关节名/维度/NaN/单调性/URDF 限位/速度加速度），
不合格会被明确拒绝并给出具体是哪个点哪个轴。

两个容易踩的地方：

- **`joint_names` 必须逐字是 `Joint1..Joint6` 且同序**。从别的机器人导来的轨迹
  即使轴数一样也会被拒。
- **`points` 里 `p` / `v` 必须各 6 个数**。少一个会报
  `第 N 个点的 p / v 必须各 6 个数`，不会被静默补 0。

自检不下发任何指令的做法：

```bash
ros2 service call /robot_arm/teach/play_trajectory robot_arm_teach/srv/PlayTrajectory \
  "{name: 'shot_arc_left_01', dry_run: true}"
```

`exit_reason: dry_run_ok` 表示九道闸里能静态判定的都过了。

## 5. 写入的原子性

`save_trajectory` 先写 `<name>.yaml.tmp` 再 `rename` 覆盖目标文件。
50Hz 录几分钟的文件不小，写一半被 Ctrl-C / 断电会留下半截 YAML，
下次加载解析失败还得人去删。`rename` 在同一文件系统内是原子的，所以要么是旧文件、
要么是完整的新文件，不会有中间态。
