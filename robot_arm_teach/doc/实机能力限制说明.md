# 实机能力限制说明

**这份文档的作用是划清「做得到」和「做不到」的边界。**
下面每一条限制都不是实现偷懒，而是既有硬件/软件栈的形状决定的——
写在这里是为了不让人对着一个做不到的能力排查半天。

---

## 0. 一句话结论

实机上目前**只有点动示教（JOG）可用**，且**只能驱动 J1-3**。
手拖示教（DRAG）在实机被明确拒绝，不做任何"看起来能用"的降级。

---

## 1. 手拖示教：实机不支持，不假装支持

### 为什么

真正的手拖示教需要 `JOINT_EFFORT`（力矩）或 `ADMITTANCE`（导纳）模式：

| 模式 | 状态 | 原因 |
| --- | --- | --- |
| `JOINT_EFFORT` | **仿真可用，实机不可用** | Gazebo 侧 2026-08-11 开通（`arm_effort_controller` + URDF effort 接口 + pinocchio 重力补偿）；实机侧 `real.launch.py` **故意不配** `effort_controller`，ModeManager 会明确拒绝切换 |
| `ADMITTANCE` | 全线未实现（P3 预留） | 需要末端 F/T 传感器，硬件没有 |

### 本包的处理

`teach.allow_drag` **默认 `false`**：

- `teach_mode: 1`（DRAG）+ `allow_jog_fallback: false` → **直接拒绝**，
  返回信息说明原因和替代做法。
- `teach_mode: 1` + `allow_jog_fallback: true` → 明确降级为 JOG，
  并在 `message` 和日志里写清降级原因与由此带来的限制。
- 即使 `allow_drag:=true`（仿真），切 `JOINT_EFFORT` 被 ModeManager 拒绝时也不静默继续。

**不做的事**：不会一边说「手拖示教已开始」一边其实只是把机械臂锁在位置模式。

### 力矩模式下「0 不是停」

这条值得单独记，因为它反直觉且后果严重：

> 位置/速度模式下发 0 就是停住；**力矩模式下发 0 是自由下垂**。
> 实测（2026-08-11，Gazebo）切进力矩模式后 J2 立刻从 +0.500 砸到下限 -0.981、
> J3 从 -1.000 砸到上限 +0.020。

所以本节点在手拖模式下**一个力矩指令都不发** —— 重力补偿 + 速度阻尼由
`mode_manager_node` 的 effort 节拍持续生成（`effort_rate_hz` 默认 100Hz，
下发 `g(q) + 用户增量 − d·q̇`）。示教需要的「用户增量」恰好是 0，
而 0 增量 ≠ 发 0 力矩：前者由节拍加在重力之上，后者会让机械臂砸下去。

若将来实机配了 `effort_controller`，重新评估前请先确认：
最大力矩夹紧（URDF `<limit effort>`）、最大速度、关节限位刹车、急停闩锁
这四件在 `mode_manager_node` 里都已具备（它们是既有实现，不是本包新加的）。

## 2. 点动只能动 J1-3，云台 J4-6 动不了

### 为什么

产品总线 `/robot_arm/cmd/joint_velocity` 的消息类型
`robot_arm_interfaces/ArmJointVelocityCommand` 里写得很清楚：

> 目标关节角速度（rad/s），顺序固定为 Joint1 / Joint2 / Joint3，**必须 3 个**。
> 云台 J4-6 不在此列 —— 本消息只驱动臂，云台保持当前角度不动。

`VelocityStreamServer` 对其他长度**直接丢弃并告警**（`关节速度指令长度 N ≠ 3，已丢弃`）。
这不是本包的选择，是既有总线的形状。

### 实际影响

- 点动示教期间云台 J4-6 **保持当前角度**，但会被**原样录进** `TeachPoint`。
  所以录出来的轨迹是完整 6 轴的，只是 J4-6 那三列是常量。
- 回放时这条轨迹照样 6 轴下发（`arm_controller` claim J1-6），云台会被"保持"到那个角度。
- 想让云台一起动，有两条既有路径，都**不经本包的点动接口**：
  - 录制前先用别的方式把云台摆到位（云台角度会被录进轨迹）
  - 用 `ArmFollowCommand` 的 6 维 twist（那是笛卡尔速度，经 Jacobian 解算 6 轴）

### 采样受云台影响的地方

`/joint_states` 6 轴不全时**采样暂停**并节流告警。云台板端未上电、
跨机 DDS 不通（`ROS_LOCALHOST_ONLY=1` 或不同 `ROS_DOMAIN_ID`）都会导致缺轴。
症状是「状态一直 RECORDING 但 `point_count` 不涨」。

**刻意不用默认值 0 顶替缺失的轴继续录**：缺回读的轴一旦被记成 0，回放时就会命令那个关节摆到 0 位。宁可暂停采样并告警。

## 3. 点动的手感：实机纹波是固有的

`JOINT_VELOCITY` 模式下，速度指令由 `VelocityStreamServer` 积分成位置流，
以 50Hz 发到 `/arm_controller/joint_trajectory`（**不是**驱动器内部速度环）。

robot_arm 侧 2026-08-12 的实机实测：

| 配置 | 跟踪率 | 速度标准差 |
| --- | --- | --- |
| 50Hz / lookahead 50ms（默认） | 71%~74% | 0.044（指令 0.15rad/s，实测在 0~0.246 之间摆） |
| 20Hz（周期 == 计划时长） | 100.4% | 0.117（纹波更大） |

机制是「下发周期 < 计划时长」使每条计划只执行 40%，而计划开头是样条最慢的一段。
**调常数只能在跟踪率与纹波之间挪，治本要换驱动器内部速度环 PV(3)**
（`velocity_backend:=velocity_controller`）。

对示教的影响：

- 点动时手感有抖动，这是既有速度通路的性质，不是示教节点造成的。
- **录下来的是实测回读**，所以纹波会一并录进轨迹。位置阈值压缩
  （默认 0.002rad ≈ 0.11°）能滤掉一部分静止期噪声，但滤不掉运动期的速度波动。
- 想要更干净的轨迹：把 `jog.max_joint_speed` 调小（慢一点纹波的绝对值也小），
  或把 `teach.compress_position_eps` 适当调大。

## 4. 回放的精度上限

| 事项 | 说明 |
| --- | --- |
| 位置环滞后 | 实机有静差，回放轨迹会被平滑、幅度略小于示教时。Gazebo 的 `SetPosition` 是运动学瞬移，实际位置恒等于设定点——**仿真的"完美复现"不能外推到实机** |
| 到位判据 | 起点判据只看 **J1-3**（`playback.start_tolerance_rad`）。末端 `gimbal_tool0` 在云台之后，判据交给云台会让每次回放都以 `not_at_start` 告终 |
| 分段带来的衔接 | 回放按 1.0s 视野 / 5Hz 滚动下发。每段被下一段替换时 JTC 从当前实际状态重新插值，理论上有极小的衔接扰动。之所以仍然分段，是因为不分段就无法暂停/停止/变速 |
| 变速延迟 | `set_playback_speed` 在当前分段走完后生效（约 `chunk_horizon_sec`）。要立刻生效就 pause → 改 → resume |
| 循环回放 | `loop_count > 1` 时整条轨迹重复。末点与首点差得远时（超过 `start_tolerance_rad`）会**自动插一段 `approach_duration_sec` 的慢速回起点**，所以每圈之间有一次可见的停顿与回程；不做首末衔接的平滑过渡 |

## 5. 自碰撞检查是**抽样**的，且可能 fail-open

- 抽样：默认最多 `playback.collision_check_max_samples`（20）个点送
  `/check_state_validity`。逐点查一条 3000 点的轨迹要 3000 次跨进程往返，
  回放请求会卡几十秒。
- fail-open：`move_group` 没跑时这道闸**放行并告警**，与
  `MoveToJointServer::collision_free()` 的既有策略一致。

抽样的风险由「示教轨迹本身是机械臂刚刚走过的路径」兜住——它天然无碰撞。
这道闸真正防的是**手改过的 YAML** 和跨机器复用的轨迹，那种问题通常是整段偏移，
抽样抓得到。但如果你手工构造了一条只有个别点越界的轨迹，抽样**可能漏掉**。

另外注意自碰撞闸看的是**6 轴组合位形**：云台停在大角度时，臂目标本身没问题
也可能被判 `collision`（robot_arm/CLAUDE.md 记过这个误判）。

## 6. 关节限位校验会 fail-open

限位从 latched `/robot_description` 解析（URDF 是唯一真相源，不写死常量——
2026-07-28 J2/J3 零点重标定就把限位整体平移过）。

`robot_state_publisher` 没跑或 URDF 解析失败时，限位表为空 → **放行并告警**
（`关节限位尚未从 /robot_description 解析到 —— 本次不做限位校验`）。

与 `robot_arm_node` 的 `JointLimitsCache` 同一策略：拿不到 URDF 就把机械臂卡死，
在实机上比不校验更糟——整台机器谁都动不了，还看不出为什么。

**这意味着看到那条告警时，限位闸实际上是关着的。** 别忽略它。

## 7. 急停 / 故障的检测是间接的

本包不直连硬件，急停状态从 `/robot_arm/arm_status` 的 `error_code` 读：

- `error_code != ERR_NONE` → 拒绝开始示教/回放；回放中则立刻停止并下发保持轨迹
- 收不到 `arm_status`（`arm_commander` 没跑）→ 默认**拒绝**
  （`safety.require_arm_status: true`）。确认机械臂正常后可设 `false` 放行
- `arm_status` 超过 `safety.arm_status_timeout_sec`（2s）没更新 → 视同收不到

拿不到状态就无法确认「没有急停/故障」，而这是回放前置条件里明确要求的一项。
所以默认宁可拒绝。

`mode_manager_node` 内部的速度总线急停闩锁（`/robot_arm/velocity_estop`）
**没有可读的状态话题**，本包读不到。闩锁生效时点动指令会被 ModeManager 丢弃
（日志刷「速度总线处于急停闩锁」），表现为「发了点动但不动」。
解除：`ros2 service call /robot_arm/reset_error robot_arm_interfaces/srv/ArmResetError`。

## 8. 关停机械臂前要显式失能

与示教无关但会一起踩到：**Ctrl-C 关停不会让电机失能**
（`ros2_control_node` 以 SIGABRT 挂掉，驱动器仍处于 Operation Enabled 带着力矩）。

关停顺序：

```bash
ros2 service call /arm_node/disable std_srvs/srv/Trigger    # 或 /robot_arm/enable "{enable: false}"
# 再 Ctrl-C
```

⚠️ 失能会让 J2/J3 失去支撑、机械臂下沉，**先确认下方无人**。
崩溃后的兜底：`cansend can0 000#8100`（NMT Reset Node）。

## 9. 不做的事（明确的非目标）

| 事 | 为什么不做 |
| --- | --- |
| 把 `TEACH` 加进 `ControlMode.msg` | 示教是上层应用状态，`ControlMode` 是底层控制方式。混成一个枚举会让 ModeManager 需要知道「示教」这个业务概念 |
| 直调 `controller_manager/switch_controller` | 会与 ModeManager 抢控制器。切模式只经 `/robot_arm/switch_control_mode` |
| 直接操作 CAN / 驱动器 | 破坏 Gazebo / MuJoCo / 实物三后端无感切换 |
| 按名字重排轨迹的关节顺序 | 能重排就意味着能猜，猜错就是让机械臂按错的轴走。名字对不上就拒绝 |
| 从 `motion_meta` 重新生成轨迹 | 元数据只是标签。回放执行的永远是录下来的关节轨迹 |
| 回放时发空轨迹来"停止" | 空轨迹不会让 JTC 停下，它会把手上那条继续执行完 |
| 修改 `robot_arm_node` 的 CMakeLists 以复用 `JointLimitsCache` | 「尽量不动既有文件」。代价是 URDF 解析代码有两份，但**限位数值的真相源仍只有 URDF 一份** |
